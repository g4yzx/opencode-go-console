## What it does

WorkBuddy's custom-model form only speaks plain OpenAI. The opencode Go gateway has a few rules of
its own: it wants a special request header, different models sit behind four different protocols,
and some models are region-locked. This project runs a relay on your own machine (bound to
`127.0.0.1` only) and absorbs all of those differences locally.

| Capability | What it means |
|---|---|
| Auth | The `x-opencode-session` header WorkBuddy never sends is generated by the bridge and attached for you |
| Protocol | WorkBuddy speaks OpenAI; the bridge translates to Anthropic / Responses / Gemini on the way out and back on the way in |
| Accounts | When one account runs out of quota, the next one is used — a half-streamed answer is never re-sent |
| Proxy | Only the models that need it go through the proxy; everything else stays direct |
| Usage | Official billing figures and local counts, side by side |
| Model install | Tick what you want in the catalog and write it into WorkBuddy's `models.json`, with an automatic backup first |

## Quick start

### Ways to run it

| Way | How | Who it suits |
|---|---|---|
| Single-file exe (recommended) | Double-click `OpenCodeGoConsole.exe`: 5–10 s unpack on first run → browser opens → lives in the notification area | No Node.js installed |
| Batch script | Double-click `start-panel.bat`; use `start-panel-silent.vbs` if you don't want the console window | Node.js 20+ installed |
| Command line | `node ui.js` | Debugging the source |

### First run, three steps

1. **Add a key** — **Accounts & Usage** (`账号与用量`) → add an account, paste your opencode key
   (`oc_sk_...`). You can add several; list order is priority order.
2. **Pick models** — **Model catalog** (`模型目录`) → **Refresh catalog** (`刷新目录`) → tick the ones
   you want → **Write to WorkBuddy** (`写入 WorkBuddy`). Use the header checkbox to select all.
3. **Start the bridge** — in the bridge box at the top, click **Start bridge** (`启动桥接`). The box
   turns green when it is up.

Then go back to WorkBuddy → Settings → Models: entries named `... (opencode Go)` should appear,
pointing at `http://127.0.0.1:8788/v1`. Clicking **Test connection** should succeed.

### What each panel does

**Bridge process** (`桥接进程`)
The relay that does the real work. Green box = running, red box = stopped; **Start bridge / Stop**
(`启动桥接 / 停止`) toggles it. You can change the port here too — the model URLs this project wrote
into `models.json` are updated to match, so there is nothing to fix by hand. While the bridge is
down, every opencode model in WorkBuddy fails immediately; other models are unaffected.

**Proxy** (`代理`)
For models that must be reached from another region. Turn it on, fill in an address (for example
`http://127.0.0.1:7897`), then tick those models in the rightmost column of the model table.
Anything unticked stays direct — nothing is routed behind your back. **Test connection** here does
more than a port check: it asks the proxy "which country are you exiting from". A reachable port is
not the same as a US exit, and this is the quickest way to see whether your proxy rules are letting
`opencode.ai` bypass the tunnel.

**Accounts & usage** (`账号与用量`)
A row of keys. Each account can be queried separately, with three windows — 5 hours, this week, this
month — showing a percentage and a reset time. Accounts can be reordered and one marked as current.
When quota runs out or a key stops working, the bridge rotates to the next one — but only before any
bytes have been written to the client. An answer that is already streaming is left alone, so you
never get billed twice or receive half an answer from two accounts.

**Usage dashboard** (`用量看板`)
Two sets of books, stacked. The top half comes from the official console (billing figures, including
usage from the opencode CLI); the bottom half counts only the requests that went through this bridge.
They are expected to disagree — the gap is "traffic that didn't use the bridge" plus "older records
that carried no token counts". Cost is estimated from models.dev prices, with cache hits charged at
the cache-read rate. It is a reference, not an invoice.

**Model catalog** (`模型目录`)
A menu. It lists what the gateway currently offers, which protocol each model speaks, its context
window and its price. You can edit context and output limits (some official figures are
conservative) and add models that are not in the catalog. Tick and click **Write to WorkBuddy** to
install them; a backup is taken first. Rows already installed are marked **Installed** (`已装`);
rows whose parameters drifted from the catalog are marked **Stale** (`旧`) and are refreshed the next
time you write them.

**Top bar** (`顶栏`)
**Auto refresh** (`自动刷新`) refreshes status and dashboards every 10 seconds without reloading the
page. The four dots next to it switch themes. The arrow at the top-right of each block collapses it,
and collapsed state is remembered.

### Common problems

| Symptom | Usually means |
|---|---|
| **Test connection** fails in WorkBuddy | The bridge is not running (red box), or the model id is wrong |
| 403 / `unsupported_country_region_territory` | This model needs a US exit; enable the proxy, tick the model, test again |
| 401 | Key invalid or lacking permission — paste it again |
| 429 | That account's quota is exhausted; add another account or wait for the reset |
| Panel opens but models fail | Click **Test** (`测`) at the end of the model row — it takes exactly the same path as WorkBuddy and shows the upstream error |

### Architecture and data flow

```
WorkBuddy ──POST /v1/chat/completions──▶ bridge 127.0.0.1:8788
                                          │ 1. resolve protocol from models-catalog.json
                                          │ 2. chat → target protocol (including SSE deltas)
                                          │ 3. pick account (rotation / direct or proxied)
                                          ▼
                                   opencode gateway /inference/go/*
                                          │
                                          ▼ responses converted back to chat.completion(.chunk)
panel 127.0.0.1:8790 ── management and observability only: accounts, catalog, usage,
                        bridge start/stop, writes to models.json
```

The bridge has no UI and no database; all state lives in a handful of JSON / JSONL files and is
restored after a restart.

Only the files worth reading are listed; launchers (`start-*.bat`, `*.vbs`) are omitted:

| File | Responsibility |
|---|---|
| `ui.js` | Panel backend: listens on 8790, serves the page and every `/api/*` route |
| `ui/index.html` | Single-page frontend, no framework, CSS and JS inlined |
| `src/bridge.js` | Bridge process: listens on 8788, protocol routing, account rotation, proxy routing, usage log |
| `src/protocol-converter.js` | chat ⇄ Anthropic Messages |
| `src/responses-converter.js` | chat ⇄ OpenAI Responses |
| `src/google-converter.js` | chat ⇄ Gemini generateContent |
| `src/usage.js` | Usage normalisation for all four protocols, plus SSE tail parsing |
| `src/official-usage.js` | Console usage (`/console/api/usage/*`) |
| `src/file-util.js` | Atomic writes, log rotation, tail-only reads |
| `accounts.js` | Account pool: candidate keys, rotation, result marking |
| `catalog.py` · `install-models.py` · `usage.py` | CLI: fetch catalog / write `models.json` / check quota |
| `pack/launcher.c` · `pack/build.py` | Tray launcher and packaging script |
| `test/` | `node --test` suites, 44 tests |

### Protocol mapping

`provider.npm` (from models.dev) selects the converter:

| npm | Protocol | Upstream path | Converter |
|---|---|---|---|
| `@ai-sdk/openai-compatible` | `chat` | `/inference/go/openai/v1/chat/completions` | passthrough (headers only) |
| `@ai-sdk/openai` | `responses` | `/inference/go/openai/v1/responses` | `src/responses-converter.js` |
| `@ai-sdk/anthropic` | `anthropic` | `/inference/go/anthropic/v1/messages` | `src/protocol-converter.js` |
| `@ai-sdk/google` | `google` | `/inference/go/google/v1beta/models/{id}:generateContent` | `src/google-converter.js` |

On the request side `messages` is split into each vendor's shape (Responses `instructions` +
`input`, Anthropic `system` + `messages`, Google `contents` + `parts`); on the response side upstream
events are merged back into `chat.completion.chunk`, including tool-call deltas and
`thinking → reasoning_content`. Unknown models return `protocol_not_bridgeable` — the bridge never
guesses.

### Endpoint reference (verified 2026-10-21)

| Purpose | Endpoint | Auth | Needs session header |
|---|---|---|---|
| Model catalog | `GET https://opencode.ai/inference/go/v1/models` | none | ❌ |
| OpenAI chat inference | `POST .../inference/go/openai/v1/chat/completions` | Bearer | ✅ |
| OpenAI responses inference | `POST .../inference/go/openai/v1/responses` | Bearer | ✅ |
| Anthropic Messages | `POST .../inference/go/anthropic/v1/messages` | x-api-key | ✅ |
| Google generateContent | `POST .../inference/go/google/v1beta/models/{id}:generateContent` | Bearer | ✅ |
| Subscription quota | `GET .../inference/go/v1/usage` | Bearer | ❌ |
| Console usage | `GET https://opencode.ai/console/api/usage/{summary,models,cost-by-day}?since=…` | Bearer | ❌ |
| Model metadata | `GET https://models.dev/api.json` → `["opencode-go"]` | none | ❌ |

- The old `/zen/go/v1/*` paths still work (kept for compatibility); new code always uses `/inference/go/*`
- Quota response: `{usage:{rolling,weekly,monthly}}`, each entry `{status,percent,resetsAt}`
- Console amounts are in `totalCostMicroCents`; divide by `1e8` for US dollars. `range=24h` stops at
  the UTC day boundary, so every request sends an explicit `since`

### Account rotation semantics

- Pool limit is 20; keys are stored in plaintext in `accounts.json` (mode 0600, current user only).
  On the WorkBuddy side any placeholder key works
- Rotation triggers: `401/403` (bad credentials), `402/429` (quota exhausted)
- **Rotation only happens before any byte has been sent to the client.** Once streaming has started,
  the response is passed through as-is, to avoid double billing and truncated answers
- `400/404`-style parameter errors do not rotate; the upstream message is passed through untouched
  so real problems stay visible
- Adding an account and querying its quota are independent paths: a failed quota lookup only records
  a log line and `lastError`, it never rolls back the account

### Usage normalisation and cost

Every request appends one line to `usage-history.jsonl` —
`{at, model, protocol, account, switched, stream, usage}` — where `usage` is normalised to
`{prompt, completion, cached, cacheWrite}`:

| Protocol | Raw fields | Handling |
|---|---|---|
| chat | `prompt_tokens` / `completion_tokens` / `prompt_tokens_details.cached_tokens` | `stream_options.include_usage=true` is injected; values come from the trailing usage chunk |
| responses | `input_tokens` / `output_tokens` / `input_tokens_details.cached_tokens` | taken from the `response.completed` event |
| anthropic | `input_tokens` (excludes cache) + `cache_read_input_tokens` + `cache_creation_input_tokens` | summed into total input; streams merge `message_start` and `message_delta` |
| google | `promptTokenCount` / `candidatesTokenCount` + `thoughtsTokenCount` / `cachedContentTokenCount` | thinking tokens count as output |

Cost uses models.dev `cost.input/output/cache_read/cache_write`: uncached tokens at the input price,
hits at the cache-read price, writes at the cache-write price. The history log rotates at 8 MB, the
diagnostic log at 1 MB, and the dashboard reads only the last 16 MB.

### Parameter fallback and two hard limits

- Upstream says `Unsupported parameter: 'xxx'` → the field is stripped and the request retried once,
  then remembered per model so it is never sent again (`top_p` also matches `topP` for Google)
- Direct connection returns `unsupported_country_region_territory` → that model is moved to the proxy
  and remembered. The host `HTTPS_PROXY` is **never** read, to avoid silently inheriting an
  environment proxy
- The Responses protocol requires `max_output_tokens >= 16`. WorkBuddy's **Test connection** asks for
  1 token, so the converter lifts it to 16
- `reasoning_effort: minimal` is invalid for Responses and is folded to `low`

Reasoning levels are parsed from models.dev `reasoning_options` into `supportedEfforts` /
`canDisableThinking`, then mapped per protocol: `chat` passes through unchanged, `responses` →
`reasoning.effort`, `anthropic` → `thinking.budget_tokens` (2048/4096/8192/12288/15360),
`google` → `thinkingConfig.thinkingLevel`.

### Catalog and models.json

`models-catalog.json` (6-hour cache) merges the gateway catalog with models.dev metadata; fields
include `protocol/context/output/images/costIn/costOut/reasoningEfforts`. An entry written to
`~/.workbuddy/models.json` looks like this:

```json
{
  "id": "gpt-6-luna",
  "name": "GPT-6 Luna (opencode Go)",
  "url": "http://127.0.0.1:8788/v1",
  "supportsToolCall": true,
  "supportsImages": false,
  "supportsReasoning": true,
  "maxInputTokens": 1050000,
  "maxOutputTokens": 32768,
  "reasoning": { "defaultEffort": "medium", "supportedEfforts": ["low","medium","high"], "canDisableThinking": true }
}
```

Manual overrides and hand-made models live in `custom-models.json` (`overrides` / `custom`) and are
shared by the panel and the CLI. Catalog-derived output limits are clamped to 65,536; manual rows may
go up to 1,000,000.

### Panel API

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/status` | Bridge, key, catalog, proxy and account summary |
| GET | `/api/catalog` | Model catalog (`?refresh=1` forces a refetch) |
| GET | `/api/usage` | Subscription quota (optional `?ref=` to pick an account) |
| GET | `/api/official/usage` | Console usage (`?days=1\|7\|30\|90`) |
| POST | `/api/test-model` | Single-model probe, same path as WorkBuddy |
| POST | `/api/install` | Write into WorkBuddy `models.json` (automatic backup) |
| POST | `/api/models` | Edit / add / remove model overrides |
| POST | `/api/accounts` | Add, edit, remove, reorder accounts and set the current one |
| POST | `/api/proxy` | Read/write proxy config and probe the exit |
| POST | `/api/config` | Change the bridge port (updates `models.json` too) |
| POST | `/api/bridge` | Start / stop the bridge |
| POST | `/api/shutdown` | Stop the bridge and quit the console (used by the tray) |

Non-GET requests must be `application/json` and are checked against `Origin`, so a cross-site page
cannot rewrite the proxy settings or stop the service.

### Packaging and process lifetime

`pack/launcher.c` (Win32, built with MinGW) plus `pack/build.py`: the application code and
`node.exe` are packed into an OCA1 archive, zlib-compressed and embedded in the exe as RCDATA.

- First run unpacks to `%LOCALAPPDATA%\OpenCodeGo` and writes a version marker to `app\.version`;
  unchanged versions are not unpacked again, and data files are not part of the payload, so they
  survive upgrades in place
- If `portable.txt` is present, the folder next to the exe is used instead (portable mode)
- Child processes are placed in a Job object (`KILL_ON_JOB_CLOSE`): however the launcher dies, node
  and the bridge are cleaned up
- The tray **Quit** item calls `/api/shutdown` first so the bridge stops gracefully; only after 6
  seconds does it fall back to `TerminateProcess`
- Launching twice does not create a second tray icon; it just brings the existing page forward
